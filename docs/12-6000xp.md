# EG4 6000XP (`ccaa`)

Analysis of the EG4 6000XP ARM "com" firmware and the basis for its entry in the
variant abstraction (`include/inv/variant.h`, `src/variant.c`,
`make VARIANT=6000xp`). Eight factory revisions were examined (2024-02 →
2026-05); all are the same MCU and codebase as the 12000XP/18kPV.

**Verdict: same MCU, same codebase — a drop-in third variant.** Structural facts
are direct reads of the images (via `tools/hex2bin.py` + `tools/vt.py`).

## Same family as the already-supported models

| property | 6000XP | how we know |
|---|---|---|
| MCU | STM32F1-compatible, M4-class core (GD32F303-style; see docs/01) | `RCC @0x40021000`, `FLASH_ACR @0x40022000` in literal pools (F1 layout) |
| C runtime | Keil armcc, scatter-loaded | reset stub is the identical `ldr;blx`→SystemInit / `ldr;bx`→`__main` idiom |
| Model code | `ccaa` | string in image |
| Image signature | `SNCC` | cf. `SNEC` (12000XP), `EAA1` (18kPV) |

## How much code is shared with the 12000XP?

**A lot — the 6000XP is a close sibling of the 12000XP, not a distant cousin.**
Beyond the shared MCU, toolchain, reset stub and `SystemInit`, code overlap was
measured directly: normalized-instruction 6-gram Jaccard similarity over each
image's full primary code segment (disassembled with resync; a *conservative
proxy* — the same C recompiled at different addresses / compiler revisions
produces different instruction selection, so this **understates** true source
sharing). What's robust is the *relative* ordering:

| pair | similarity | note |
|---|---|---|
| 12000XP-05xx vs 12000XP-07xx | **50.9 %** | two eras of the *same* product (reference ceiling) |
| 6000XP vs 6000XP (two eras) | **78.8 %** | 6000XP self-consistency |
| **6000XP vs 12000XP** | **25.6 %** (13,006 shared 6-grams) | close sibling |
| 6000XP vs 18kPV | 5.0 % | distant |
| 12000XP vs 18kPV | 3.4 % | distant |

So the 6000XP shares **~5× more code with the 12000XP than with the 18kPV**, and
about **half as much as two revisions of the 12000XP share** with each other. The
common core is the whole platform: boot/clock/vectors, the Modbus-RTU stack, the
HMI render engine, the settings model, and the DSP link. The **18kPV is the
diverged outlier** (hybrid, 3-MPPT).

A clean structural tell: the **interrupt architecture is identical**. In both the
6000XP and the 12000XP exactly two IRQs have dedicated handlers — **USART3** and
**PVD** (brown-out / power-fail save) — while all 58 other IRQs share one default
self-loop handler. Same design, same handler spacing.

## DSP link — same protocol, same UART (USART3)

**Yes: the 6000XP talks to the TI C2000 DSP the same way the 12000XP does.**

- **USART3 is the only interrupt-driven serial port** on both (USART1/2 are
  polled → default handler). USART3 is the ARM↔DSP link (DSP SCI-B), exactly as
  documented for the 12000XP in [`docs/08`](08-arm-dsp-config-protocol.md).
- **The USART3 ISR is the same routine** — a thin wrapper
  `push {r7,lr}; bl <rx_handler>; pop {r0,pc}` (12000XP `→0x080013A8`, 6000XP
  `→0x08001320`): byte-identical but for the shifted call target. The adjacent
  PVD handler matches too.
- USART3 is referenced the same amount (6 literal refs in each monolithic build),
  and the comms + CRC code sits inside the shared core above.

The ARM→DSP config-push protocol (Modbus-family frame envelope, **type-1** frames,
the **9-block** full-snapshot scheme, CRC-16 trailer; `docs/08`) is therefore part
of the shared core — the 6000XP uses the **same protocol over the same UART**.
What differs is the *field-level content* of the blocks (e.g. 2-MPPT payloads,
model-specific settings), the same way block contents already vary across 12000XP
variants.

> **Scope of this claim:** the *transport* is verified line-for-line (the USART3
> ISR is the same routine) and the comms stack is demonstrably in the shared core.
> The 9-block frame *builder* was not byte-traced in the 6000XP (that needs a
> recursive disassembler); all transport + structural evidence points to it being
> the same code, but it is stated as inference, not a line-by-line confirmation.

## Boot layout — and its revision history

The 6000XP exists in both a **monolithic** form (vector table at the flash base,
`0x08000000`) and a **bootloader + App** form (vector table relocated to
`0x08005000`, low 20 KB reserved for a bootloader) — the same two layouts the
12000XP uses across its 05xx→07xx history (`docs/11-12000xp-revisions.md`). The
App form is what `make VARIANT=6000xp` targets:

| | App form (current) |
|---|---|
| Vector table / VTOR | `0x08005000` (SystemInit writes `SCB->VTOR`; literal at `0x080249DC`) |
| Low 20 KB `0x08000000..0x08004FFF` | reserved for a bootloader (absent from App dumps) |
| App top | `0x0803F7FF` (256 KB boundary; `SNCC…` signature at `0x0803F600`) |

Revisions examined (hex-code order; `xxNNxx` is the firmware code, NN in hex):

| code | file | date | vectors | layout | flat bytes |
|---|---|---|---|---|---|
| xx0A | `ccaa-xx0Axx_3` | — | `0x08005000` | App | 155,300 |
| xx0B | `ccaa-xx0Bxx_com_2` | — | `0x08005000` | App | 155,340 |
| xx0C | `ccaa-xx0Cxx_2_comm` | 2024-02-04 | `0x08000000` | monolithic | 168,464 |
| xx0D | `ccaa-xx0Dxx_comm` | 2024-08-09 | `0x08000000` | monolithic | 179,416 |
| xx10 | `ccaa-xx10xx` | 2025-03-22 | `0x08000000` | monolithic | 184,216 |
| xx12 | `ccaa-xx12xx_comm` | 2025-08-06 | `0x08000000` | monolithic | 199,036 |
| xx14 | `ccaa-xx14xx` | 2026-01-22 | `0x08005000` | App | 198,584 |
| xx15 | `ccaa-xx15xx` | 2026-05-19 | `0x08005000` | App | 198,616 |

The dated images run monolithic (2024-02 … 2025-08) then App (2026-01 →); the
undated xx0A/xx0B are App-layout, so their exact place in the timeline is
uncertain. Either way the descriptor models both via `layout` / `vector_addr` /
`bootloader_size`.

## The HMI strings are NOT in the com-MCU firmware

The 6000XP has a built-in LCD HMI much like the 12000XP, so its menu text was
expected to be in these images. **It is not — in any of the eight revisions.**
This was checked exhaustively, and the conclusion is backed by several
independent lines of evidence:

1. **No ASCII, ever.** `grep` for `Charge`/`Battery`/`Yield`/`Standby`/`Lithium`/
   `Model`/`Language`/`Volt` → **0 hits in every 6000XP image** (forward *and*
   reversed), vs. 1–4 each in the 12000XP. Not a partition artifact: the
   monolithic images (full flash from `0x08000000`) lack them too.
2. **Not a simple transform.** Single-byte XOR/ADD/SUB sweeps, 16-bit wide-char
   (both phases), nibble-swap and bit-reverse against cribs (`Charge`, `Yield`,
   `Battery`, …) all come up empty.
3. **Not compressed.** No high-entropy blob — the densest 2 KB blocks sit at
   ~6.6 bits/byte (ordinary ARM code); a packed string resource would spike
   toward 8.
4. **No label-pointer table.** The 12000XP builds its menu from a **118-entry
   pointer table** (`0x080062d4`) into an ASCII blob — readable straight out:
   `"Grid Always On:"`, `"PV Grid Off:"`, `"Fan1 Max Speed:"`, `"SN: "`, … **No
   6000XP revision has any such table** (its only tight pointer pools are the ISR
   vectors and the `SNCC…` signature).
5. **No in-image font.** The ~39 KB segment at `0x08031800..0x0803B000` present
   in every revision is a **second code bank**, not a font: it is only ~8%
   identical across revisions (a font resource would be ~100%).
6. **The clincher — the string region is reserved but blank.** The 12000XP
   stores its strings in `0x0802C000..0x08031800` (≈30% populated with ASCII).
   In **every** 6000XP revision that identical address range is **100 % `0xFF`** —
   the layout reserves the space and ships it empty.

### The draw path (disassembled)

The 12000XP renders text itself: `sub_0800f1b8` is a framebuffer text routine —
takes a `char*`, scans to NUL (≤ 50 chars), bounds-checks an 80×160 graphic LCD —
and `sub_08005938` populates the menu table from the in-flash ASCII pointers
above. The 6000XP runs the **same engine** (same codebase) but the data it would
read is simply **not present** in the com image.

### Conclusion

The 6000XP com-MCU firmware carries the **logic only**. Its HMI **strings and
font live outside these images** — the com/App build reserves the region
(`0x0802C000..0x08031800`) and leaves it `0xFF`, to be populated by a separately
flashed **resource / font / language image**. That is why no revision reveals the
text, and why feeding in more com/App revisions will not surface it.

**To recover the 6000XP menu strings, the resource image is required** — a
companion `ccaa` artifact (not the `_com`/`_comm`/App logic file), or a full
flash dump from a unit that includes the populated `0x0802C000+` region. The LCD
text could then be read directly (the renderer draws plain ASCII, as on the
12000XP). A Ghidra recursive pass on the 6000XP menu path can confirm the exact
source pointer, but the six lines of evidence above already settle it.

## Topology is spec-derived

The descriptor's `mppt_count` / `phase_count` / `hybrid` come from the EG4 6000XP
product spec (6 kW off-grid, **2 MPPT**, **non-hybrid**, split-phase 120/240,
generator input), not from the image — these App partitions carry no HMI strings
to confirm them in-band. The firmware consequences match the 12000XP: 3rd-MPPT
Modbus registers gated off by `inv_ir_active()`, hybrid-only features disabled.
