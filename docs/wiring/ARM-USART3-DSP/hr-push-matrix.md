# HR → DSP push matrix (T25)

> For every writable dongle **holding register**, whether a write **reaches the
> DSP** config push and, if so, which **block · offset** it lands in — the
> side-effect half of every setting (T03 covers storage; this covers propagation).
> Generated by [`tools/dsp_push_matrix.py`](../../../tools/dsp_push_matrix.py)
> against the factory flat image. See the [index](fields.md),
> [hr-controlled-fields](hr-controlled-fields.md) and
> [block-03_06](block-03_06-gridcharge-slots.md).

## Method — two fresh single-write captures (not `push_delta`)

Each register is written at two distinct in-range values **on two separate fresh
boots**, and the resulting config-frame payloads are diffed. A byte that differs is
driven by the register's **value**. This deliberately avoids the differential
`push_delta(reg, A, B)` (write A then B on *one* sim), whose second-write-follows-
first **modbus-transaction residue** is a false positive — that is how "HR 75 →
block 4 `0x26`" was once wrongly "verified" (single-write: `0x26` is constant, so
HR 75 is stored-only). Cross-boot builds are deterministic (verified: two fresh
boots with the same write produce byte-identical blocks), so the diff is clean.
Value-dependent residue lands only at payload `0x15/0x16` and block 0 `0x25/0x26`
(shared modbus-RX buffer) and is classified out; this sweep leaked **none**.

**Status column:**
- `writable` — both test values stored; the diff is meaningful.
- `inert` — neither value read back (feature/mode-gated or validated-out in the
  default boot). **Not** proof of read-only.
- `1-value` — only one of the two values stored (e.g. HR 145 accepts only its
  default here, HR 194 start-V clamps below end-V), so the register **cannot be
  exercised live with this value pair** — left to static analysis, not a "no push".

## Key findings

- **Block 6 is not a "constant template".** Its body is the lead-acid **and
  generator** charge parameters: HR 101 charge-curr `0x17`, HR 102 discharge-curr
  `0x1b`, **HR 194 gen start-V `0x1d`, HR 195 gen end-V `0x1f`, HR 196 gen start-SOC
  `0x21`, HR 197 gen end-SOC `0x22`, HR 198 max-gen-curr `0x23`**, HR 99 charge-volt
  `0x25`. Our firmware now emits all eight byte-for-byte (T10). Only the `0x19` word
  (const `0x012c`) is still undecoded.
- **Block 0 carries packed config/enable bytes**, not just an identity template:
  HR 120 `SYS_ENABLE` → `0x19`, **HR 90 EPS-volt + HR 91 EPS-freq share packed byte
  `0x1a`** (freq = bit `0x08`), HR 110 `FUNCTION_EN1` + HR 112 `SET_SYSTEM_TYPE`
  share `0x1c`, HR 20 `PV_INPUT_MODEL` → `0x28`, HR 21 `FUNC_EN` → `0x2c`. (These
  are the decode targets to finish block 0; the T10 identity/version constants at
  `0x15…0x18`, `0x1b…0x22` remain a separate template.)
- **HR 112 `SET_SYSTEM_TYPE` is multi-target** (block 0 `0x1c` + block 3 `0x19`).
- **Windows** (HR 68–73 → block 4, 152–157 → block 5) and **block-3 EOD/backflow**
  (105/103) confirm the T10 spec.
- **ARM-local only** (writable, pushes nothing — effect evaluated ARM-side): HR 11,
  15, 59, 60, 62, 64, 65, 66, 75, 126, 147, 148.
