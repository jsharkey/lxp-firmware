# HR → DSP push matrix (T25)

> For every writable dongle **holding register**, whether a write **reaches the
> DSP** config push and, if so, which **block · offset** it lands in — for both the
> factory image and **our firmware**. The side-effect half of every setting (T03
> covers storage; this covers propagation). Generated by
> [`tools/dsp_push_matrix.py`](../../../tools/dsp_push_matrix.py). See the
> [index](fields.md), [hr-controlled-fields](hr-controlled-fields.md) and
> [block-03_06](block-03_06-gridcharge-slots.md).

## Method — two fresh single-write captures (not `push_delta`)

Each register is written at two distinct in-range values **on two separate fresh
boots**, and the resulting config-frame payloads are diffed. A byte that differs is
driven by the register's **value**. This deliberately avoids the differential
`push_delta(reg, A, B)` (write A then B on *one* sim), whose second-write-follows-
first **modbus-transaction residue** is a false positive — that is how "HR 75 →
block 4 `0x26`" was once wrongly "verified" (single-write: `0x26` is constant, so
HR 75 is stored-only). Cross-boot builds are deterministic, so the diff is clean.
Value-dependent residue lands only at payload `0x15/0x16` and block 0 `0x25/0x26`
(shared modbus-RX buffer) and is classified out; this sweep leaked **none**.

**Status words:** `inert` = neither test value stored; `1-value` = only one of the
two stored (not exercisable live, not proof of "no push"). The **ours** column is
the same sweep on our firmware; **agree** is `y` when ours moves the same field set
the factory does.

## Result

**31 of 59 writable HRs push to a block. Ours agrees with the factory on every one
except HR 112.** HR 112 `SET_SYSTEM_TYPE` is multi-target — the factory writes
block 0 `0x1c` *and* block 3 `0x19` (a parallel-system role lookup `{0→0x3a98,
1→0xfffe, 3→0xfffe}`); ours emits the block-0 contribution only, by design (ours is
a non-parallel build and the block-3 lookup's semantics are unresolved).

## Key findings

- **Block 6** carries the lead-acid **and generator** charge parameters: HR 101/102
  currents, HR 99 charge-volt, **HR 194–198 generator charge**.
- **Block 0** is packed config/enable bytes, not an identity template: HR 120
  `SYS_ENABLE` → `0x19`; HR 90 EPS-volt + HR 91 EPS-freq + **HR 146 LINE_MODE** share
  `0x1a`; HR 110 `FUNCTION_EN1` + HR 112 `SET_SYSTEM_TYPE` share `0x1c`; **HR 100
  cut-voltage → `0x21`**; HR 20 → `0x28`; HR 21 → `0x2c`; HR 145 priority → `0x1e`.
- **HR 100 and HR 146 were found by resolving the `1-value` rows** with storing value
  pairs the first sweep's A/B had missed — the bytes `0x21` and `0x1a`-bit-`0x20` the
  old block-0 map had read as constant template are really these two settings.
- Still **`1-value`** (only one value stores in the bare boot, can't differentiate
  live): HR 16, 113, 145 (145 is static-confirmed → `0x1e`).
- **ARM-local** (writable, pushes nothing — effect evaluated ARM-side): HR 11, 15,
  23, 59–66, 75, 126, 147, 148.

Our firmware emits all 30 reproducible fields byte-for-byte; routing is locked
ours==factory by [`test_dsp_push.py`](../../../tests/test_dsp_push.py)
(`DSP_PUSH` windows + `GRID_PUSH` scalars + `test_ours_matches_factory_absolute`).
