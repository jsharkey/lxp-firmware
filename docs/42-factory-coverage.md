# 42 — Factory-coverage dashboard

**How much of the factory firmware have our parity tests actually exercised?**
This is the long-term "are we there yet?" metric for the reimplementation: a
single, reproducible number (plus a worklist) for how much of the factory image
our `test-sim` suite drives while asserting our firmware matches it.

The live figures are in [`factory-coverage.md`](factory-coverage.md),
regenerated by `make factory-coverage` (or as a side effect of `make test-sim` when a
factory image is present). This doc explains what the number means, how it's
computed, and how to extend it.

## The idea

`make test-sim` already runs the proprietary factory image under the Unicorn
harness ([`tools/arm_sim.py`](../tools/arm_sim.py)), so the *same* black-box
tests assert our reimplementation behaves identically ([`docs/19`](19-gpio-test-harness.md)).
That means we can **watch which factory functions actually execute** while those
tests run — and a factory function we execute is one our tests both *drove* and
*pinned our behaviour against*.

So the metric is **dynamic function coverage of the factory image, measured over
the parity suite**:

```
                in-scope factory functions executed ≥ once
   coverage  =  ──────────────────────────────────────────
                all recovered functions − the ignored ones
```

We report it two ways: a plain **function count**, and an **instruction-weighted**
figure (each function weighted by its `insns` count from
[`reference/symbols.csv`](../reference/symbols.csv)), so a 4-instruction leaf
doesn't score the same as a 360-instruction controller.

## Why function-level (not line/instruction %)

The function map is recovered, not authoritative: `recurse.py` reconstructs
~72% of the image as code and its function **boundaries are heuristic**
([`docs/03`](03-function-map.md)). A line- or instruction-percentage would imply
a precision the map doesn't have. Function-level is the honest altitude — "we
drive N of the M factory functions we care about" — with the instruction-weighted
number as a sense of *mass* exercised. It is deliberately a breadth metric.

## How it's wired

Three moving parts, all committed; only the *measurement* needs the proprietary
image.

1. **Collection** — [`tools/arm_sim.py`](../tools/arm_sim.py). When
   `$LXP_COVERAGE` names an output file **and** the loaded image is the one named
   by `$LXP_COVERAGE_IMAGE`, every `ArmSim` adds one `UC_HOOK_BLOCK` that records
   the entry PC of each executed basic block. PCs are flushed, de-duplicated, to
   the file at interpreter exit — *appended*, so the separate test processes
   `make test-sim` spawns accumulate into one capture. The image-path match
   scopes collection to the factory oracle, so the "ours" and cross-image sims in
   the same run never pollute it. Collection is **pure observation**: it never
   changes a test's pass/fail, and it is off unless both env vars are set, so
   ordinary runs pay nothing.

2. **The denominator & ignore list** —
   [`tests/factory_coverage_classify.csv`](../tests/factory_coverage_classify.csv)
   (hand-curated) plus
   [`reference/hmi_functions.csv`](../reference/hmi_functions.csv) (the
   machine-found HMI set, below). Every recovered function is `in_scope`,
   `ignore`, `unreachable`, or (the default) `unclassified`. Only `ignore` and
   `unreachable` are removed from the denominator; **`unclassified` stays in
   it**, so the score can never be flattered by simply *not* triaging a hard
   function. Each hand entry carries a reason, held to the repo's
   claims-discipline bar ([`AGENTS.md`](../AGENTS.md)).

3. **The dashboard** — [`tools/coverage_report.py`](../tools/coverage_report.py)
   maps the captured PCs onto the function map, applies the classification, and
   writes [`factory-coverage.md`](factory-coverage.md): headline + weighted %, a
   per-module table, and a **ranked worklist of the biggest unexercised in-scope
   functions** — the actionable part: pick one, write a black-box `test-sim` case
   that drives it on both images.

Everything except the *covered* set is derivable from committed, non-proprietary
artifacts, so with no capture the dashboard still renders the full in-scope
surface as a 0%-measured worklist — honest, and useful on day one.

## Finding the HMI code to ignore

[`tools/hmi_classify.py`](../tools/hmi_classify.py) locates the factory's
menu/display code statically and writes
[`reference/hmi_functions.csv`](../reference/hmi_functions.csv) (addresses +
evidence — the proprietary image never enters the tree). The method:

- **Roots** — functions whose literal pool references the on-screen string data
  or one of the menu string-pointer **tables** (the 93-entry settings menu at
  `0x08005fec`, docs/03), plus the menu handlers docs/03 named from their text.
- **Closure** — everything those roots call (the formatters and the bit-banged
  LCD panel driver, docs/28). The call graph
  ([`reference/callgraph.txt`](../reference/callgraph.txt)) includes
  literal-pool indirect calls, so it reaches past the obvious edges.
- **Barrier** — the closure is intersected *out* of what the real entry points
  (Reset + the ISR/exception vectors) can reach **without** passing through an
  HMI root, so a helper shared with control code is never pulled in. Because the
  recovered call graph is sparse (it reaches ~160 functions from the entry
  points), this barrier only ever *protects* — it can shrink the HMI set, never
  grow it, which is the safe direction.

**Static closure over-approximates, so the dashboard prunes it dynamically.**
When we first ran it, 37 of the ~100 statically-HMI functions turned out to be
executed by the functional parity tests — settings handlers named after menu
text (`fn_Lead_Acid_Floating_Voltage`) that also drive config, a 4109-insn
worker, and so on. So the rule the dashboard applies is: **an HMI-list function
is ignored only if the functional tests never execute it.** One a test *does*
drive stays in scope and counts. This matches the repo's "dynamic outranks
static" discipline, makes the ignore set shrink automatically as the suite
grows, and means the score can't be gamed by ignoring code we actually test. The
`hmi` row in the dashboard's module table is exactly those HMI-list functions
the tests still reach.

## Running it

```bash
# Full dashboard against the factory image (needs the proprietary .hex/.bin):
LXP_FACTORY_HEX=/path/to/vendor.hex make coverage
#   → writes docs/factory-coverage.md

# Or it falls out of a normal sim run when an image is present:
make test-sim        # regenerates the dashboard as a non-fatal side effect
```

With no factory image, `make test-sim` behaves exactly as before (ours-only,
green) and leaves the checked-in dashboard untouched — only someone holding the
image regenerates it. The proprietary binary never enters the tree; the
committed inputs are the derived symbol CSV and the classification CSV.

## What the number does and does NOT mean

- **Covered ≠ correct.** Executing a factory function proves a test *drove* it;
  the actual agreement comes from the shared assertions in that test, not from
  this number. Coverage is **breadth of exercise, not depth of equivalence**.
- **Function-hit is an upper bound on confidence.** A function entered on one
  trivial input counts covered even if its fault/edge branches never run.
- **The denominator is the _recovered_ map**, not every function that exists.

Keep those caveats in view: this metric is a map of *where we've looked*, a
companion to the parity assertions — not a proof of faithfulness on its own.

## Next steps

- **Grow the HMI set as the call graph improves.** The static closure is a
  conservative floor: the recovered call graph misses indirect calls through RAM
  dispatch tables, so some display code is reached only by edges we can't see
  yet and stays `unclassified` (counted against us — the safe direction). Better
  edge recovery, or a dynamic HMI-navigation capture (drive the factory menu in
  `tools/factory_hmi_app.py` and diff its executed set against the functional
  tests'), would extend `reference/hmi_functions.csv`.
- **Module tags.** As each subsystem is triaged, tag its functions
  (`modbus`, `can-bms`, `dsp-config`, `acfirst`, `safety`, `persistence`) so the
  per-module table shows *where* the gaps are, not just the aggregate.
- **Optional CI ratchet.** A separate, opt-in check that fails only if the
  in-scope percentage drops below a committed watermark — kept out of the
  `test-sim` green/red contract so it can't pressure anyone to erode the ignore
  boundary.
