# 18kPV vs 12000XP — comparing the two factory ARM "com" images

This document compares the **ARM "com" MCU** firmware of two EG4 all-in-one
inverters and establishes how much of the codebase is shared. It is the basis
for the variant abstraction added to this project (`include/inv/variant.h`,
`src/variant.c`).

Everything below is a **direct read** from the two factory Intel-HEX images
unless explicitly marked *(inferred)*. Analysis was done against correctly
addressed flat images (`tools/hex2bin.py`), not the raw text.

| | 12000XP | 18kPV |
|---|---|---|
| Image file | `…_ceaa-05xx_com_vE_250325.hex` | `…_FAAB-1Bxx_20240528_App.hex` |
| Role of this MCU | comms / HMI / supervisor | comms / HMI / supervisor |
| Hardware | **non-hybrid, 2 MPPT** | **hybrid grid-tie, 3 MPPT** |

> The 12000XP image here is byte-identical in content to the one this repo was
> already built from (244,080 present bytes — same as the `…_com_vE_250325.bin`
> recorded in the README). The 18kPV is new to the project.

## TL;DR

The two firmwares are the **same codebase**, compiled for two product variants
with a slightly different Keil toolchain revision. The MCU, the C runtime, the
clock bring-up, the peripheral set and the Modbus/HMI/DSP architecture are all
shared. The real differences are a short, enumerable list:

1. **Flash/boot layout** — the 12000XP is a single monolithic image; the 18kPV
   ships as an **App above a ~50 KB bootloader**, so its vector table is
   **relocated to `0x0800C800`**.
2. **MPPT count** — 2 vs 3 (the 18kPV adds a 3rd PV tracker: `Vpv3/Ppv3/Epv3*`).
3. **Hybrid features** — the 18kPV is grid-interactive (export-to-grid,
   AC-couple); the 12000XP is not.
4. **Model/signature markers** — `ceaa`/`SNEC` vs `FAAB`/`EAA1`.

## 1. Same MCU: STM32F1-compatible, M4-class core

> The core is **ARMv7E-M (M4-class), not Cortex-M3** — the factory image executes
> `smlabb`/`sdiv` (undefined on M3). STM32F1 peripherals + an M4 core = a
> **GD32F303-style F1 clone**. See [`docs/01`](01-firmware-analysis.md) /
> [`docs/19`](19-gpio-test-harness.md). Both variants are the same part.

Both images reference the STM32F1 peripheral bases in their literal pools:

| peripheral | address | 12000XP refs | 18kPV refs |
|---|---|---|---|
| RCC | `0x40021000` | ✓ (20) | ✓ (15) |
| FLASH ACR | `0x40022000` | ✓ (17) | ✓ (8) |
| GPIOA / GPIOB | `0x40011000` / `0x40011400` | ✓ | ✓ |
| USART1 / USART2 / USART3 | `0x40013800` / `0x40004400` / `0x40004800` | ✓ | ✓ |
| CAN1 | `0x40006400` | ✓ (3) | ✓ (6) |

`RCC @ 0x40021000` and `FLASH_ACR @ 0x40022000` exist **only on STM32F1** (on
F2/F4 they are `0x40023800`/`0x40023C00`). Both populate MemManage/BusFault/
UsageFault vectors (rules out M0) and expose 60 external IRQs (the F1
high-density map); the core is M4-class (see the note above). The 18kPV references CAN1 and USART1 somewhat more heavily,
consistent with its extra tracker and richer parallel/BMS comms *(inferred)*.

## 2. Same C runtime and clock init (same source, different compiler rev)

**Reset stub** — identical idiom in both (Keil armcc: call `SystemInit`, jump to
the scatter-loaded `__main`):

```
ldr r0,[pc,#4] ; blx r0     ; -> SystemInit
ldr r0,[pc,#4] ; bx  r0     ; -> __main (scatterload)
<literal: &SystemInit>
<literal: &__main>
```

| | 12000XP | 18kPV |
|---|---|---|
| initial MSP (`vector[0]`) | `0x200008D0` | `0x20000478` |
| reset handler (`vector[1]`) | `0x08002980` | `0x0802B788` |
| `SystemInit` | `0x0800231C` | `0x0802AEA0` |
| `__main`/scatterload prologue | `nop.w; nop.w; bl …` | `mov r8,r8 ×4; bl …` |

`SystemInit` in both is textbook **CMSIS-F1**: set HSION, clear `RCC->CFGR`,
disable HSE/CSS/PLL, clear `RCC->CIR`, then configure HSE+PLL and set `VTOR`.
The only substantive delta is that the 18kPV additionally clears a `CFGR`
bitfield (`0x14000000`) during reset — a minor clock-config difference. The
`__main` prologue differs only in how NOPs are encoded (`nop.w` vs the
`mov r8,r8` Thumb-nop alias), which is a **compiler-version** difference that
tracks the build dates (2024-05-28 vs 2025-03-25), not a source difference.

Implication for this project: our reimplementation (`arm-none-eabi-gcc`) is
functionally equivalent, not byte-identical, for **both** targets — same as the
existing non-goal of byte-matching.

## 3. Flash / boot layout — the biggest structural difference

`tools/hex2bin.py` recovers the true flash segments:

**12000XP** — monolithic, vectors at the flash base, fills a 512 KB part:

```
0x08000000 .. 0x080029FF   vectors + early startup
0x08004E00 .. 0x0803031D   main code
0x0803151E .. 0x0803EF67   code + HMI string/font tables
0x08040000 (4B), 0x0807F7FC (4B)  markers  ("SNEC" @ top of 512K)
```

**18kPV** — a single contiguous **App** region that starts well above the flash
base, because a bootloader occupies the low flash (not included in `App.hex`):

```
0x08000000 .. 0x0800C7FF   (reserved for the bootloader — ABSENT from App.hex)
0x0800C800 .. 0x0803F7FF   App: vectors @0x0800C800, code, "EAA1" @0x0803F7FC
```

So the 18kPV **relocates its vector table to `0x0800C800`** (≈ 50 KB / `0xC800`
of bootloader below it) and tops out at the 256 KB boundary (`0x08040000`). The
12000XP boots at `0x08000000` and tops out at 512 KB.

This is the one difference that the firmware bring-up *must* honor: `SCB->VTOR`
has to point at the App's real vector address. The abstraction drives it from
the variant descriptor (see §6).

## 4. Model identity and parameter tables

Each image carries factory markers and a model-default block:

| | 12000XP | 18kPV |
|---|---|---|
| 4-char model code | `ceaa` (@`0x0802F3C8`) | `FAAB` (×3, @`0x0802B5E8`) |
| top-of-image signature | `SNEC` (@`0x0807F7FC`) | `EAA1` (@`0x0803F7FC`) |
| other markers | `SNECNOTBSNFC`, `SNECSNEDEDSNDPOTLAA1SA22` | `2AAEA2EA`, `LCD0DPOT`, `EAA1` (@`0x0800D000`, `0x0801BF44`) |

The 18kPV's `FAAB` marker is immediately followed by a packed defaults block
(`00 00 10 00 01 00 01 00 fa 00 f4 01 …`) — a per-model parameter table. The
12000XP's `ceaa` marker is followed by battery-telemetry labels (`eTower`,
`Vbat:`, `Ibat:`, `Pchg:`, `SOC:`, `SOH:`). These codes are what a shared
codebase keys its model-specific behaviour on; decoding the default block is a
good follow-up.

## 5. Functional deltas (topology → features)

From the hardware (maintainer-confirmed) and the Modbus superset
(`include/inv/modbus_map.h`), corroborated by recovered HMI strings:

| Feature | 12000XP | 18kPV | Evidence |
|---|---|---|---|
| PV trackers (MPPT) | 2 | 3 | HMI "Same for 2 MPPTs", "PV1,PV2,independent" (12K); `Vpv3/Ppv3/Epv3*` map |
| 3rd-tracker registers (IR 3, 9, 30, 44, 45) | unused (read 0) | live | Modbus map note |
| Hybrid grid-tie | no | yes | maintainer; hybrid grid-tie-only map items |
| Export / feed-in to grid | no | yes | `HR_MAX_BACKFLOW`, export regs |
| AC-couple external GT inverter | no *(menu present, inactive)* | yes | HMI "AC Couple …" strings |
| Generator input + gen-charge | yes | yes | HMI "Generator Charge …" both |
| Output | split-phase 120/240 | split-phase 120/240 | map/HMI |

> The 18kPV App partition does **not** embed the big HMI string/font tables (it
> extracts far fewer readable strings than the monolithic 12000XP). Those
> resources live in the bootloader/resource region that is outside this
> `App.hex`, so the 18kPV's menu text could not be read here directly. The
> feature list above is anchored on the Modbus superset and the 12000XP strings,
> and should be refined once an 18kPV resource dump is available.

## 6. What this means for the open firmware

The split is clean: **one codebase, a small variant descriptor**. The deltas map
onto data, not divergent code paths:

- **Memory/boot** → `inv_variant_t.{layout, vector_addr, bootloader_size,
  flash_size}`; `SystemInit` writes `SCB->VTOR = inv_variant()->vector_addr`,
  and the build selects `ldscripts/stm32f103ve.ld` (12000XP) or
  `ldscripts/stm32f103_18kpv_app.ld` (18kPV, FLASH origin `0x0800C800`).
- **Topology** → `mppt_count`, `hybrid`, `phase_count`.
- **Feature gates** → `feat_export_to_grid`, `feat_ac_couple`,
  `feat_generator_port`, plus `inv_ir_active()` to blank the PV3 registers on a
  2-MPPT build so the Modbus superset stays well-formed.

Build either target:

```bash
make                 # EG4 12000XP (monolithic, vectors @0x08000000)
make VARIANT=18kpv   # EG4 18kPV   (App over bootloader, vectors @0x0800C800)
make test            # host tests, incl. tests/test_variant.c (both descriptors)
```
