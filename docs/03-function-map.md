## How this firmware is built (affects RE technique)

It is **Keil/armcc**, and almost every inter-function call is **indirect**:

```
ldr  rX, [pc, #imm]   ; load a function pointer from the literal pool
blx  rX               ; call through it
```

So a naive "follow BL" disassembler recovers almost nothing (it did: 30
functions). `recurse.py` therefore also treats **odd (Thumb) code pointers
found in literal pools** as function entries — that is how the firmware itself
reaches its code — plus a `push {...,lr}` prologue scan for anything still
missed. That combination is what lifts coverage to ~72%.

## Known limitation: string-based auto-naming

Only **1** string is referenced by a direct `ldr =string` literal. The HMI
stores its text as **pointer tables** (`const char *menu[]`) indexed at runtime,
so string→function association needs a *pointer-table resolver*, not literal
scanning. This is the top next tooling task because those same tables encode the
**menu tree** — recovering them names a large fraction of HMI functions at once.

### Next tooling steps
1. **Pointer-table resolver**: scan flash data for runs of ≥2 words that each
   point to a string start → recover `char*` arrays (menus, unit labels, fault
   text) and the functions that index them.
2. **Jump-table (TBB/TBH) decoding** to resolve switch targets the sweep stops at.
3. Emit a Ghidra import script (`.py`) that applies `symbols.csv` so the
   interactive workspace starts pre-labeled.

## Using it as the shared workspace (optional Ghidra recipe)

Import the raw binary as: **ARM Cortex, little-endian**, load address
`0x08000000`, then run Auto-Analyze. Apply `reference/symbols.csv` to name
functions. The memory map and peripheral bases are in `docs/01-firmware-analysis.md`.
